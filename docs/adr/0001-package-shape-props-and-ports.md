# 0001. Package shape: a server-safe core, a player and an editor, and three ports

- **Status:** Accepted
- **Date:** 2026-11-12

## Context

`learn-sdk` is the family's first SDK that isn't about a media file. [ADR 0035](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0035-ai-core-and-host-configured-network.md) admits kinds that aren't media; everything else in [`STANDARDS.md`](https://github.com/ie-huss-martinez/sdk-core/blob/main/STANDARDS.md) still applies, but its editor contract is written for files: `file` and `onChange`, `filePolicy`, `engine` and `processor`, `assets`. A learning SDK has no file and no engine. It has:

- **content:** exercises written by a teacher, imported, or generated by the host, as plain data;
- **two audiences:** learners answer exercises in a **player**; teachers write them in an **editor**;
- **learners' data:** answers, results and spaced-repetition state, which belong to the host and its learners, not to the SDK;
- **hosts on both sides of the network:** a browser shows the player, and a server, such as a Cloudflare Worker behind a school's app, must grade the same answers with the same code, so a learner can't send in their own score.

The family's first consumer is a private language-learning app with a school portal. It grades on a Worker and shows exercises on tablets, so both sides are real from the start.

## Decision

### Entries ([ADR 0004](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0004-entry-points-and-module-format.md))

| Entry | Contents |
|---|---|
| `.` | The headless core: the content model, `parseContent`, the exercise-type registry and the built-in types' validation and grading, the course model and `canAccessCourse`, the player and editor sessions, the ports, `LearnError`, `learnLimits` and the message catalogue. **Server-safe:** no React, no DOM and no browser globals on import or when grading, in Node and in Workers runtimes. A test imports it and grades in plain Node with no DOM globals; another runs in workerd. |
| `./react` | `LearnPlayer`, `LearnEditor`, a player and an editor building block per exercise type, and hooks (`useLearnPlayer`, `useLearnEditor`). Starts with `"use client"`. |
| `./element` | `defineLearnPlayerElement()`, registering `<hm-learn-player>` on the family's element base ([ADR 0040](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0040-editor-element-base.md)). Registers nothing on import. |
| `./styles.css` | All styles, in `hm.sdk`, with `.hm-learn-*` classes. |
| `./standalone` | A self-contained script for plain HTML pages, added with the element. |

### The content model

- **Content** is plain, serialisable data: `{ version: 1, exercises: Exercise[] }`. An **exercise** is `{ id, type, title?, instructions?, payload }`, where `type` names a registered exercise type and `payload` is that type's data.
- **`version`** is the format's version. A future format change adds a migration from the previous version; content without a known version is rejected ([ADR 0002](0002-content-as-hostile-input.md)).
- **Courses:** the core also models courses, levels and enrolments, with `canAccessCourse(learner, course)`: a learner sees exactly the courses they are or were enrolled in, a set and never a range. Hosts use it on their servers to decide what to send; the SDK never fetches anything.

### Exercise types

- **`defineExerciseType({ type, validate, validateAnswer, grade })`** registers a type. All three functions are pure:
  - `validate(payload, context)` returns the payload, rebuilt from known fields, or the issues found ([ADR 0002](0002-content-as-hostile-input.md));
  - `validateAnswer(answer, payload)` does the same for a learner's answer;
  - `grade(payload, answer, profile)` returns `{ score, max, items }`, where `items` marks each item right or wrong, so the player can show which ones were.
- **Built-in types,** each in `src/features/<type>/` with its validation, grading, player, editor, styles and messages: multiple choice, gap fill, word order, matching, flashcards, dialogue and listening.
- **Hosts can register their own types** with the same contract. A host type is validated and graded through the same functions, so it gets the same protections.
- **Exercise types are content types, not tools.** Actions in the player and editor, such as check, next, retry, add exercise, undo and redo, are tools registered with `defineTool`, with shortcuts from the family registry ([ADR 0030](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0030-tools-and-keyboard-shortcuts.md)).

### Language profiles

A **language profile** is a plain value, not a port: `{ code, direction, normalizeAnswer?, segment? }`.

- `normalizeAnswer(text)` must be deterministic string operations. Grading applies NFC normalisation first, then the profile's function. Thai, for example, ignores the spaces learners type between words.
- `segment(text)` is for display only, such as offering words as tiles in the editor. Grading never calls it, and never uses `Intl.Segmenter`, ICU data or the locale, whose results differ between runtimes. Word-order payloads store their tiles explicitly.

### Sessions ([ADR 0029](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0029-session-store-and-history.md), [ADR 0010](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0010-edits-as-commands.md))

- **The player session** is a store of the current attempt. Answering, checking, moving to the next item and retrying are commands through a `Reducer`.
- **The editor session** is a store with history: every edit is a serialisable command, with undo and redo. Destructive edits, such as deleting an exercise, offer undo instead of a confirmation.

### Props, mapped from `STANDARDS.md`

| `STANDARDS.md` | `learn-sdk` |
|---|---|
| `file` + `onChange`, or `initialFile` | **Editor:** `content` + `onChange`, or `initialContent`. **Player:** `content`, read only. |
| (no equivalent) | **Player:** `progress` + `onProgress`, or a `progressStore` port: what the learner has done, and each change as it happens. |
| `engine`, `processor` | Ports: `audio` (`AudioSource`), `progressStore` (`ProgressStore`) and `scheduler` (`Scheduler`). |
| `assets` | None: the SDK has no worker or WebAssembly. |
| `filePolicy` | `limits`: the host's settings for `learnLimits` ([ADR 0002](0002-content-as-hostile-input.md)). |
| `tools`, `toolbar`, `features` | `tools` and `toolbar` as in the family; `types` lists the exercise types available, built in or the host's. |
| `onEvent` | Unchanged, under the privacy rules of ADR 0003. |
| `theme`, `className`, `classNames`, `unstyled`, `messages`, `locale`, `icons` | Unchanged. `profile` adds the language profile. |

Ref handles: the player's `check()`, `next()` and `reset()`; the editor's `undo()`, `redo()` and `getContent()`. `<hm-learn-player>` takes `content`, `progress` and `limits` as properties, never attributes, and dispatches `hm-learn-player-progress` and `hm-learn-player-complete`.

### Ports ([ADR 0008](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0008-ports-adapters-and-session.md))

Each port has a fake for tests and a contract-test suite that every adapter, including hosts' own, must pass.

- **`AudioSource`:** `load(ref, { signal })` resolves to a `Blob`, an `ArrayBuffer` or `null`. The host turns a content's opaque audio reference into bytes; the SDK never fetches. Speech synthesis is never built in. Both are recorded in ADR 0003.
- **`ProgressStore`:** `load(scope)` and `save(changes)`, for attempts and spaced-repetition state. Adapters: in memory (the default) and an opt-in device-storage adapter, both in ADR 0003.
- **`Scheduler`:** `initial()` and `review(state, rating, now)` for spaced repetition, with an FSRS adapter (ADR 0004). Its state is opaque to the rest of the SDK.

## Alternatives considered

- **`file` and `filePolicy` as in the media SDKs:** content is often not a file. It comes from a host's database or is generated, and calling it a file would mislead hosts about where validation happens.
- **One component for players and editors:** their users, permissions and failure modes differ. A learner must never reach editing, and a teacher's editor needs history and validation feedback that a player doesn't.
- **Grading in the React layer:** a server couldn't grade, and learners could send their own scores.
- **Language specifics in the core,** such as Thai word segmentation: grading would depend on ICU and differ between runtimes, and every host would carry every language's rules. Profiles keep them in the host.
- **Fetching audio by URL inside the SDK:** a request the SDK makes, against [ADR 0012](https://github.com/ie-huss-martinez/sdk-core/blob/main/docs/adr/0012-hostile-input-and-no-network.md), and one the host can't authorise or cache.

## Consequences

- One package serves learners' screens and servers' grading, and a host can embed a single exercise in any page through the element.
- Hosts write three small adapters, or use the defaults: audio is the only one with no default, because only the host knows where its audio lives.
- The content format is versioned from the start, so it can change without breaking stored content.
- New exercise types must ship validation, grading, a player, an editor, messages and keyboard support together, which keeps them slow to add but complete.
