# Security policy

`@hussmartinez/learn-sdk` displays and grades learning content inside other people's applications: exercises written by teachers, imported from files or generated by a host. It also handles learners' answers and progress, which belong to the host and to the learners. A vulnerability here can run script in a school's or an app's pages, let a learner game their results, or leak learners' data, inside every application that embeds the SDK. Reports are among the most valuable this project can receive. Thank you for taking the time to report one privately.

## Reporting a vulnerability

**Please don't open a public issue, pull request or discussion.**

Report it through GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**, or go directly to [the advisory form](https://github.com/ie-huss-martinez/learn-sdk/security/advisories/new). Only the maintainer can see the report.

Please include:

- the affected version, or the commit;
- what an attacker can do, and under which conditions;
- steps to reproduce it, or a proof of concept. If it needs crafted content, attach it to the private report. **Never attach real learners' answers, names or progress, or a school's course material.** Use made-up content, or describe how to make it.

## What to expect

- **Acknowledgement** within 7 days.
- **Updates** at least every 14 days until the issue is resolved.
- **A fix and an advisory.** Once a fix is released, a GitHub Security Advisory describes the issue, with a CVE where it applies. You're credited in the advisory unless you'd rather not be.
- **Coordinated disclosure.** Please keep the issue private until the advisory is published, or for 90 days after your report, whichever comes first. If a fix needs longer, we'll agree on a date with you.

## Supported versions

The package is pre-1.0. Security fixes go into the latest release only. No version has been published yet.

## Scope

In scope is everything in this repository: `@hussmartinez/learn-sdk`, its validators, grading, components, adapters and custom element, the workflows that verify and release it, and the published package. Examples:

- **script or style injection:** content that runs script in the host page, or that the SDK inserts as HTML, Markdown or a link, such as a prompt, a choice, a note, a dialogue line, a vocabulary entry or a media reference; or content that changes the page's styles outside the component;
- **content bombs:** content beyond the configured limits ([ADR 0002](docs/adr/0002-content-as-hostile-input.md)), in bytes, exercises, items, choices, words, pairs or string lengths, that is still parsed, validated or rendered; deeply nested or adversarial JSON, such as `__proto__` keys, that changes objects it shouldn't; or content that makes validation, grading or rendering hang, crash the page or exhaust memory;
- **grading integrity:** an answer that earns marks it shouldn't, for example through unexpected types, extra or missing items, or out-of-range indexes; content the validator accepts but grading can't handle; or the same answer graded differently in different runtimes, such as a server and a browser, or two browsers;
- **any network request** the SDK makes, including for media named in content, speech synthesis, fonts or telemetry; or audio played from anything other than the bytes the host supplied;
- **learners' data leaks:** answers, progress, scheduling state, names or content reaching the host's `onEvent`, error details or logs; device storage used without the host opting in, outside its namespace, or trusted when read back; or one learner's or one player's answers or audio showing in another on the same page;
- styles from the standalone script that change the host page outside the SDK's components;
- anything that requires a weaker Content Security Policy than documented;
- weaknesses in the build, release or publishing workflows, such as unpinned actions, excessive permissions, or a bundled dependency that doesn't match its pinned version.

**A known vulnerability in any third-party code that the SDK bundles is in scope** when the SDK's latest release still ships the affected version, because applications can only get the fix from us.

Out of scope:

- a host application's own server, accounts or storage, such as the endpoint that receives graded attempts. Report those to the application;
- mistakes in a host's learning content, such as a wrong answer key. Report those to the content's author;
- issues that need an already compromised device, browser or build environment;
- content that is merely slow within the configured limits. Report it as a public issue;
- accessibility defects. They matter just as much, but report them as a public issue so they can be fixed in the open.

Vulnerabilities in the shared runtime or the design system go to their repositories' security policies: [sdk-core's](https://github.com/ie-huss-martinez/sdk-core/security/policy) and [ui's](https://github.com/ie-huss-martinez/ui/security/policy).
